## Station invalidation after tracking pause/resume — log-derived diagnosis

Evidence: `Xiaomi-2201117TG-Android-13_2026-10-29_193032.logcat` (231k lines).
Two full failure cycles in it; the first (line refs):

- L51170/51965: targets 1, 2 captured automatically (drift 0.027/0.072 m).
- L65555: drift warning entered raw=0.205 (user walking to target 3; rose to
  0.304 before pause) — **genuine translation**, calculation correct.
- L68660 @3397.5: `tracking->paused`, epoch 3→4. `_beginRecoveryVerification`
  sets `_recoveryStartedAt` **at the boundary**.
- L76940 @3399.981: `paused->tracking`.
- L79025 @3400.587: station invalidated, message "could not restore the
  selected station anchor" — **0.606 s after resume** = exactly 3.0 s after
  the boundary (`kRecoveryVerificationTimeout` measured from the pause).

### Proven defects

1. **Recovery timeout measured from the pause boundary, not the resume.** A
   >3 s pause leaves an arbitrarily short post-resume window (0.6 s here)
   before forced invalidation. ARCore relocalisation takes seconds.
2. **The no-placement else branch made zero restoration attempts** — no
   `_refreshAnchorIfDue()`, nothing; it just waited out the timeout. The
   message "could not restore" was literally true.
3. **Refresh-success did not restore `activeAnchored`** — if the flag was
   lost across the pause, the controller stayed in the no-placement branch
   forever even though the host re-confirmed the placement.
4. **Camera-jump check false-positives on real walking**: same-anchor jump
   >0.43 m invalidated the station even when ARCore still held the identical
   anchor (drift rose 0.137→0.205→0.304 m from real walking pre-pause).

### Architecture note (changed since 10-27)

Single **shared station anchor** now (anchor-3 for all 30 targets). The
`gone` branch of `_refreshAnchorIfDue` intentionally invalidates instead of
re-placing (single-target re-place would reintroduce the drifting-target
bug). `_recoverTarget` is dead code — defined, never called.

### Fixes applied (capture_controller.dart, capture_state.dart, ar_capture_screen.dart)

1. Grace restarts at resume (`_recoveryStartedAt = _clock()` when
   `trackingResumed && _recoveryVerificationPending`).
2. `_refreshAnchorIfDue()` now called in the recovery else branch — attempts
   restoration; gone → honest immediate invalidation; held → verification.
3. Refresh-success emits `activeAnchored: true` (cannot fake readiness —
   tracking + verification + stability still required).
4. Same-anchor camera jump during recovery → reseed comparison + restart
   hold (translation), NOT invalidation; different-anchor jump still
   invalidates. Same-anchor means ARCore vouches for world identity.
5. `ARCORE_STATION_DIAG` transition-only trust-state line
   (trusted / recovering:boundary / recovering:resumed / invalidated) with
   epoch, anchor id, anchored, placement state — the `anchored=`/
   `placement=` fields will disambiguate WHY the else branch was reached
   (open question: `activeAnchored` false vs `_placement` null).

Dropped mid-implementation: a `_recoveryReplacedAnchor` tolerance — dead
code under the shared-anchor architecture; removed before finishing.

## Follow-up: ring never completes despite "aligned" — refinement threshold fix

Fourth logcat (220722): targets 1-3 captured, target 4 stuck. Rejections:
angular-rate ×11, window ×13, sample-gap ×3, orientation-drift ×1. Ring
failure root cause CONFIRMED: `kAnchorRefinementResetM = 0.01` /
`kAnchorRefinementResetDeg = 0.6°` — stricter than the hold's own stability
tolerances (0.03 m / 1.5°), so routine ARCore map refinements (the log's
0.015 m / 3.50°) restarted the hold almost continuously.

Fixes:
- `_hasAnchorRefined` now measures the **target world position** movement
  against the hold baseline (threshold = `maxPositionDriftM` 0.04 m) instead
  of the anchor's own translation+rotation — an anchor rotation about the
  target's bearing moves the target not at all, so 3.5° of anchor rotation
  alone no longer resets anything. `kAnchorRefinementResetM/Deg` removed;
  `_anchorStabilityOrientationReference` removed.
- Thresholds relaxed in `vio_sphere_math.dart` (the single source —
  `CaptureGeometryConfig` defaults to `VioSphereConstants`, so UI and engine
  stay consistent): alignment 3→**4°**, hold 600→**450 ms**, angular
  velocity 5→**8°/s**, orientation drift 1.5→**2°**, position drift
  0.03→**0.04 m**, sample gap unchanged 150 ms, station drift unchanged
  0.20 m (bypassed separately).
- Reset-reason guidance already existed (`_settlingInstruction` maps every
  engine rejection to a sentence in the instruction line); ring fill is
  gated by `displayCaptureBlockReasonBeforeSettle` so it cannot fill while
  any non-stability condition fails.
