## Round 4 (two screen recordings: missing arrow, capture loop, target flicker, size)

No video was attached to the session — traced from the source and the written
symptoms. Two of the four were **defects introduced the round before**; both
now fixed.

* **Missing arrow — root cause: the gate I added.** `anchored:` had become
  `activeAnchored && activeAnchorTracking`, but ARCore *pauses* anchors whenever
  its tracking degrades and (since round 2) a paused anchor is still **drawn**.
  So during every pause the marker stayed on screen and the pointer vanished.
  Fixed: `anchored = activeAnchored` (the node's world position is what the
  arrow needs) plus a new `poseValid = tracking == TrackingState.tracking` —
  the arrow is a projection *through the camera pose*, so a stale pose gives a
  dishonest direction. `instruction` honours the same condition, so the pointer
  and the sentence cannot disagree.
* **Repeated capture / "Ready ↔ Saving" flicker with the count stuck at 0/26 —
  root cause: `captureBlockReason` never mentioned a failed attempt.** A target
  whose photograph kept failing stayed "ready", and with the auto shutter that
  is fire → fail → fire → fail forever. Fixed with two latches:
  `_captureInFlight` (synchronous, taken before `_shoot`'s first await; the old
  code read `state.capturing`, which is *published* state and can lag a frame)
  and `CaptureState.retryPending` (set on both failure paths; cleared only by a
  deliberate move off target — error past `tolerance + hysteresis`, the same
  threshold that breaks the stability window, so hand tremor cannot re-arm it).
  `_shoot` split into latch-holding `_shoot` + `_runCapture` so the `finally`
  cannot be bypassed.
* **Target disappearing/reappearing — root cause: visibility was keyed on
  `shotPhase`**, which folds in `measurementFresh` and camera `tracking`. Both
  flip on their own (a pose gap over 250 ms, a momentary pause) → the marker
  flashed. Fixed: `CaptureState.ringComplete` (withinTolerance **and** stable,
  both already hysteretic) plus `capturing` plus `isDone`. Readiness is
  deliberately not consulted. Concepts kept apart: ring / transaction /
  accepted / readiness.
* **Inconsistent size — no scaling defect.** Verified end to end: `widthX` is the
  post-node-transform bounds (`GlbDrawable.min/max`), `buffersFor` bakes the
  same transform into the uploaded vertices, `markerScaleFor(0.54) ≈ 0.407` is
  applied once at `boot` to plate *and* bezel, `ArSceneDraw.scale` is never
  re-derived, native `buildModelMatrix` applies scale exactly once (`A·R·T·S`),
  and all 26 draws share one `markerScale`. Apparent variation is perspective;
  the status detail prints "Plate 0.22 m across · N.NN m away". No distance
  compensation added (explicitly forbidden).

Files: `capture_state.dart` (ringComplete, retryPending, tracking-aware
instruction), `capture_controller.dart` (latches, visibility rule),
`target_alignment_overlay.dart` + `ar_capture_screen.dart` (arrow gates),
`WORKFLOW_VERIFICATION_capture_pipeline.md`. No tests/analyze/build; no device.

## Round 5 (confirmed to proceed after the tool preflight)

Two remaining defects, both fixed.

* **Problem 2 root cause — the ring and the shutter used different conditions.**
  The ring filled on `withinTolerance && stabilityProgress`, but
  `readyToCapture` additionally requires `!stationDrifted` and
  `activeAnchorTracking`. So the ring sat at 100% while the shutter was blocked
  and the target stayed on screen — exactly "ring complete, nothing happens".
  Fix: split `captureBlockReason` into `captureBlockReasonBeforeSettle` (every
  condition except the window) + the settle check; the ring's fill is gated on
  the former, and `ringComplete` (visibility) includes it too. Now
  ring-full ⟺ `readyToCapture`. `_shoot`/`captureNow`/auto path already shared
  the latch from round 4; verified `autoCapture = true` by default and the
  screen does not override it.
* **Problem 1 root cause — the guidance and the renderer read two different
  target positions.** The renderer draws from `anchor.pose` every frame; the
  alignment used `placement.worldPosition`, refreshed on a 500 ms timer. Fix
  (the smallest supported API change): `ArCoreGateway.setActiveAnchor(id?)` →
  Kotlin keeps the id in an `AtomicReference` and `emitPose` puts that anchor's
  current translation + tracking state on the pose event it already emits;
  `ArPoseSample.activeAnchorPose` is what the alignment uses, with the cached
  position as fallback. Zero extra channel calls. Controller names the anchor on
  selection/recovery and clears it on rescan/recalibrate/retry/unplaced.
  Verified **no** placement defect: `resolveTarget`/`StationFrame`/`placeAll`
  correct, `buildDraws` reads `anchor.pose`, model = `A·R·T·S`, no
  `GL_CULL_FACE`, `quaternionToMatrix` matches the Dart convention, 26 stable
  anchor ids, `selectTarget` touches status only.

## Round 6 ("targets still move with the phone") — no rendering defect; proof added

Traced the whole chain again with fresh eyes. **Placement and rendering are
correct, and now proven by execution**, not by reading:

* `resolveTarget` has exactly ONE call site — `plane_anchor_service.placeAll:167`
  — reached only from `calibrateStation`, `rescanActive`, `_recoverTarget`. No
  per-frame call. Camera pose is used only for the station origin at
  calibration, the record, the alignment and drift.
* New `tool/verify_sphere.dart` (standalone, like `tool/measure_glb.dart`):
  places all 26 through the real `resolveTarget` and moves the camera four ways.
  **Worst world movement 0.0e+0 m**, radius error 2.2e-16 m, yaw 0.0°, pitch
  7.1e-15°. Screen projection moves (centre → edge → off-screen); facing stays
  fixed (`facing·toCamera` 1.0 → 0.24) so it is not a billboard.
* Native verified: `mvp = P·V·(A·R·T·S)`, `A` from `anchor.pose` per frame, no
  `GL_CULL_FACE`, `quaternionToMatrix` == the standard column-major quaternion
  matrix (cross-checked against `Quat.toMatrix3`'s row-major twin), Dart sends
  `px/py/pz/qx/qy/qz/qw` in the order Kotlin reads.
* `tool/verify_all.dart` is **stale** — imports `test/*_checks.dart` files that
  no longer exist; do not register new tools with it.

**The one real defect found and fixed: a paused pose was being used as current.**
`_onPose` derived the alignment and the drift figure from a pose ARCore flags as
possibly stale. Growing drift from it is what blamed the user for the tracker's
own uncertainty ("you are 0.9 m from the station, walk back" while they never
moved). Fix: `trackingOk` is now part of `placementIsActive`, so a paused pose
yields no alignment (cleared instead), `driftM` holds its last trustworthy value,
`stabilityProgress` resets, and the auto shutter is structurally unreachable.
Targets untouched throughout.

**Conclusion to carry forward:** the residual "targets move when I rotate" is
ARCore world-map drift under `INSUFFICIENT_FEATURES` (the screenshots' own
message), not a code defect — the markers are correct in ARCore's world, and
ARCore's world is what slides. Only a device in a textured room can confirm.

Verification: `dart format --output=none --set-exit-if-changed lib test tool`
→ clean; LSP analysis (probe-verified pipeline) → **0 errors / 0 warnings,
120 files**; `dart run tool/verify_sphere.dart` → the numbers above. No
tests/builds; no device.
