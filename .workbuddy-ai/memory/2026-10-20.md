## Invisible-next-target bug — root cause + fix (new brief)

Symptom: first GLB visible; after its capture the first disappears and the
next never appears.

**Root cause: a re-entrancy race in the accept → next-target transition, with
zero prior test coverage** (`bootHarness` hardcoded `autoAdvance: false`, so
`_shoot` → `_nextPending` → `selectTarget(next)` had never been executed by the
suite):

1. `selectTarget` releases the old anchor and then *awaits* creating the new
   one. A pose arriving in that window (guaranteed at 30–60 Hz on device) drove
   `_refreshAnchorIfDue` into its "anchor is gone" branch — true only because
   the placement itself just released it — which started a **second concurrent
   `selectTarget`**: two anchors, two scene pushes, scene can reference the
   anchor the state flags don't describe. Paused anchor in scene +
   `activeAnchorTracking: true` = renderer draws nothing, no waiting message.
2. A refresh that captured anchor 1 *before* the swap answered *after* it and
   wrote anchor 1's id/position onto target 2's record.
3. `_onPose`'s alignment branch checked only `_placement != null`; `_placement`
   still held target 1's placement while `activeTargetId` was already 2 → the
   arrow aimed at the released target.

**Fix** (`capture_controller.dart`, `plane_anchor_service.dart`):
- `PlaneAnchorService.refresh()` now returns
  `AnchorRefreshOutcome({placement, gone, stale})` and does the swap-detection
  **inside itself, before mutating `_active`** — the controller-side id check
  was useless because `refresh()` overwrote `_active` before the `.then` ran.
- `_refreshAnchorIfDue` captures `requestedId` at call time and skips while
  `_placing`; the service discards answers about replaced anchors.
- `selectTarget` serialized with `_placing` + a one-slot `_pendingSelection`
  queue (last request wins, drained in `finally`); host exceptions become a
  refusal instead of an unhandled async error.
- `_onPose` alignment branch gated on `next.activeAnchored`
  (`placementIsActive`), so a stale placement can't aim the arrow.
- `_nextPending` made position-based (list index) instead of relying on
  `targetId == index + 1`.
- Diagnostics: `--dart-define=capture_transition_log=true` traces active
  target, anchor ids before/after, duplicate/stale discards, refusals.

**Tests**: new `test/target_transition_test.dart` (15): 26-target arrangement
invariants, one anchor per target across 26 selections, 1→2→3 transitions,
26 captures on one session with exactly 26 anchors and one live anchor, the
mid-flight-pose race (reproduced: 3 anchors instead of 2), the stale refresh
(reproduced: target 2's record pointed at `anchor-1`), overlapping selections
(reproduced: leaked anchor), failed capture/validation preserving the current
target, retry placing once, plate-faces-station at all 26 incl. zenith/nadir.
Test infra: `anchorGate`/`refreshGate` hooks in the fake, `autoAdvance` param
on the harnesses.

**Gotcha learned the hard way**: the station frame is a **mirror**
(`localToWorld` negates local x: station +X is the physical right, `−q·x̂`).
Test expectations for world positions/directions must go through
`frame.localToWorld(spec.direction)` — `spec.direction × radius` is wrong.

Verified: analyze clean, **238 tests pass** (223 → 238, two consecutive full
runs), APK built. Two first-run failures were async-photo-completion flakes
under load; hardened with a bounded `Harness.waitFor` (outcome, not machine).
Device still unavailable — on-device 1→2 verification pending.

## Persistence audit (same brief, second pass)

Brief items §7–§9 asked about the "database schema". **There is no SQL layer in
this project** — the real store is `FileCaptureRepository`
(`lib/features/capture/data/repositories/`): `<appDocs>/ar_capture/<stationId>/`
with `station.json` (the station record, `stationId` is the directory name AND
the primary key), `targets.json` + `records.json` (both carry `stationId` as the
FK; `targetId` is the frame index), `frames/tNN.jpg`. Production generates the
station id (`station-<epoch-ms>`); nothing hardcodes one. `saveRecord` already
replaced by `targetId`, so retakes never duplicate. Target/verdict/blocked
status logic was inspected and found correct (already test-covered).

**Three real defects found and fixed in `capture_controller.dart`:**
1. **`FileCaptureRepository.saveRecord` threw on the first record of every
   station** — `loadRecords` returns the shared `const []` when the file does
   not exist yet and `saveRecord` called `removeWhere` on it
   (`Unsupported operation: Cannot remove from an unmodifiable list`). In
   production this meant every station's FIRST photograph failed to record:
   the JPEG landed, the target was marked failed, no count, no advance. Fixed
   with a defensive `List<CaptureRecord>.of(...)` copy. Found by the new
   real-store tests, not by inspection — the repository had **no test at all**.
2. **Failure paths never persisted**: `_shoot`'s `on CaptureFailure` and
   generic `catch` emitted the failed status but never `saveTargets` — after a
   resume the target read as "never attempted". Both now persist.
3. **`retake` never persisted the decremented station count**: the station
   record kept counting the retaken target, reporting one more photograph than
   existed on disk. Now re-saves the station with the recomputed count.

Tests: new `test/capture_persistence_test.dart` (5, against the REAL
repository in a temp dir — station PK/FK round-trip, 26 targets filed under
their station, retake-replaces-record, cross-station isolation, frame paths);
+2 in `target_transition_test.dart` (failure persisted, retake count
persisted). 238 → **245 tests pass**, two consecutive full runs, analyze
clean, APK built.

Another load-flake fixed the honest way: `captureActive` now waits for
`state.stable` before pressing the shutter — under load the fixed flush left
the last emitted poses queued, the gate read "not stable", and the iteration
silently captured nothing. Gate on the precondition, not the machine.

**Tooling note**: the Write tool silently drops `content` above ~6 KB, and
large `cat << EOF` heredocs intermittently vanish (no file, exit 0). Reliable
pattern: heredoc/Write in chunks of ≤ ~4 KB, verify with `wc -l` after each.

## Gravity-aligned reference + all-26 nodes (brief round 3)

Two architecture changes, both verified by tests that fail on the old code:

1. **Gravity-aligned capture reference.** `calibrateStation` used to freeze the
   raw camera pose, pitch and roll included — calibrating while looking 20° up
   tilted the entire 26-target sphere by 20°. New pure helpers in
   `station_frame.dart`: `projectOntoHorizontal`, `elevationAboveHorizontalDeg`
   and `captureReferenceFromPose({cameraForward, gravityUp, maxVerticalityDeg})`.
   The reference is rebuilt from two vectors: world `+Y` (gravity — ARCore fuses
   the accelerometer, so it is phone-roll-free) as up, and the camera's optical
   axis **projected onto the horizontal plane** as forward, which keeps the
   user's yaw and drops their pitch and roll. `R·x̂ = up × forward` completes
   the basis, keeping the project's `−R·x̂` = screen-right convention. When the
   camera points within `kMaxCalibrationVerticalityDeg` (10°) of vertical the
   projection is noise, so calibration is **refused with a stated reason** — no
   invented fallback heading.
2. **All 26 nodes placed once, kept for the session.** `PlaneAnchorService` now
   holds `Map<targetId, anchor>` + placements. `placeAll` is idempotent by
   target id (retries create only what is missing; a refusal is a per-target
   failure with a reason, the other 25 still place). `selectTarget` no longer
   places anything — it moves the highlight (opacity: active opaque, done
   targets keep the done tint at full opacity, everything else a ghost at
   0.35) and aims the guidance. The only post-calibration placement is
   `_recoverTarget` — a bounded re-place of ONE dropped anchor. All placements
   run through `_withPlacementSlot` so a selection during a placement queues
   and drains. `_refreshAnchorIfDue` refreshes only the active target's anchor
   and discards answers whose target moved on. `rescanActive` releases all and
   re-places all (idempotent), never restarting the session.

Tests: `test/capture_reference_test.dart` (8 — level/tilted/rolled calibration,
near-vertical refusal at the documented boundary, and the money test: a 20°
pitched calibration still yields middle-ring elevation exactly 0°, upper +45°,
lower −45°, zenith +90°, nadir −90°, front target == the projected heading,
back target opposite). `target_transition_test.dart` rewritten for the new
model: 26 nodes at calibration (distinct ids, distinct positions, 52 draws),
selection touches no node, 1→2→3 progression with **zero** anchor churn, all 26
captures with exactly 26 anchors live, placement frozen mid-pass (no
duplicates), selection-during-recovery queued, stale refresh discarded,
overlapping selections place nothing. 245 → **255 tests pass**, analyze clean,
APK built. Device still unavailable.

## Brief round 5 (front-first, false-completion map) — 3 real defects fixed

1. **Sphere map showed every dot amber at "0 of 26 captured"** (user
   screenshot). Root cause: the calibration placement pass stamped
   `CaptureTargetStatus.active` onto **all 26** placed targets, and the map
   paints `active` amber. Placing a node is not activating a target.
   `_withAnchorIn` now takes `setActive` (default false); only `selectTarget`
   and the recovery mark the one target being aimed at. Second half of the
   same bug: `selectTarget` never demoted the previously-active target, so
   every visited target stayed highlighted — added `_demoteActive`.
2. **The capture sequence started on an upper-ring target** (yaw 0, pitch +45).
   `buildCaptureSphere` is reordered front-first: id 1 = front (middle, yaw 0,
   pitch 0), 2–8 the rest of the middle ring, 9–16 upper, 17–24 lower,
   25 zenith, 26 nadir. Same 26 directions, 8/8/8/1/1, poles still at 25/26.
   `CaptureTargetSpec.shortName` added for guidance ("Move to the front
   target. Turn right 45°" — `CaptureState.instruction` now names the target).
3. **No resume path existed.** Added `CaptureRepository.stationIds()`
   (only directories holding a station record count), `savedStationIds` /
   `resumableStationId` refreshed at boot and after each save, and
   `CaptureController.resumeStation(id)`: rebuilds the target rows from the
   **saved records** (done only where a record exists), re-saves the station
   with the record-derived count, re-places the arrangement idempotently and
   starts on the first uncaptured target. Unknown/malformed stations refuse.
   UI: "Resume last capture" ghost button next to Calibrate.

Tests: new `test/capture_progress_test.dart` (11 — first target is the front
horizontal target, instruction names it, exactly one active target with all
others pending, moving the active flag, progress 0→+1 per accepted frame,
repeat capture doesn't double-count, failed capture leaves count and target,
26/26 only with all 26 accepted, resume restores from records with no node
duplication, a new station inherits nothing, unknown station refuses).
265 tests pass, analyze clean, APK built. Device still unavailable.

## Brief round 6 (oversized GLB, placement authority, stuck "Hold still") — 3 defects

1. **Marker ~2.5× too large.** The plate is authored 0.54 m across (bezel
   0.70 m) — the asset was never the problem; the *scale* was a bare constant
   `1.0`, so at the 1.5 m radius it subtended ~20° and filled a third of the
   view. `CaptureGeometryConfig` now has `targetDiameterM` (0.22 m) and
   `markerScaleFor(modelWidthM) = targetDiameterM / measuredWidth`
   (`GlbMeshSource.targetWidthM/bezelWidthM`); the service holds the resolved
   `markerScale`, set by the controller after the meshes load. 0.22 m at 1.5 m
   is ~8.4° — aimable, not dominating.
2. **Two sources of placement truth.** `resolveTarget({station, spec, radius})`
   in `target_sphere.dart` is now the single authority (position + facing +
   rotation); `facingRotation` moved from the data service into the domain so
   the domain function can use it; `placeAll` calls `resolveTarget`. Test pins
   map↔world agreement: `worldToLocal(worldPosition − origin)` returns the
   `spec.direction` the sphere map draws, for all 26.
3. **"Hold still…" forever.** Two structural causes, both in the stability
   gate: (a) the window was thrown away whenever the raw error crossed the 3°
   shutter tolerance — hand tremor around the boundary cleared it every few
   frames, so `heldFor` never reached 450 ms; added
   `alignmentHysteresisDeg` (2°) so the *window* tolerates tremor while the
   *shutter* still requires the strict tolerance. (b) The platform gyro rate
   was trusted directly, and a gyro bias of several °/s on a still phone
   refuses forever; the pose-derived rate is now the authority and a platform
   figure only counts when the poses corroborate motion. Plus the instruction
   now names the blocker ("Hold still — moving at 7.4°/s", "Waiting for a fresh
   pose…", "Hold still — re-aiming at the front target").

Tests: new `test/target_scale_test.dart` (14 — real-asset width/front-face,
scale normalisation, subtended angle < 12°, bezel ratio, front/back/right/left/
upper/lower/zenith/nadir, map↔world agreement, fixed positions, readiness
wording) and 6 new stability cases (tremor, biased gyro, genuine walk, stale
pose, hysteresis both sides). 286 tests pass, analyze clean, APK built.
Device still unavailable — thresholds unchanged pending hardware measurements.
