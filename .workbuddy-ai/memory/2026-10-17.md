# 2026-10-17

## Section 1 — AR capture module (real ARCore)

Implemented the Capture module on top of the existing Flutter project. Before this
work the project had a complete AR *abstraction* (`ArPoseSource`,
`ArStationAnchorSource`, `ArFrameGrabber`, `arcore_payload.dart`) but no AR host:
`ar_bootstrap.dart` shipped `SensorPoseSource` and stated "This build has no ARCore
host". The GLB target was drawn by a pure-Dart triangle projector over the camera
preview, i.e. a HUD, not an anchored model.

### Decisions worth remembering

- **Native ARCore host, not a pub plugin.** `android/.../ar/` contains
  `ArCoreCapturePlugin.kt` (MethodChannel + EventChannel + Flutter Texture),
  `ArCoreSessionController.kt` (GL thread, session, raycast, anchors, stills),
  `ArGlRenderer.kt` (camera OES texture + mesh program), `YuvJpegEncoder.kt`
  (YUV_420_888 → rotated NV21 → JPEG). Reason: Section 1 needs an arbitrary
  world raycast, an anchor at that hit, the live pose, *and* a still taken through
  the running session. ARCore owns the camera exclusively, so CameraX cannot
  supply the still. No maintained Flutter AR package exposes all four, and the
  Sceneform-based ones would replace the two shipped `.glb` assets.
- `com.google.ar:core:1.48.2` was **already** on the app's Gradle classpath and
  the manifest already declared `com.google.ar.core` = optional. Only the Kotlin
  host was missing.
- **Mesh data crosses the bridge, not the model file.** Dart parses the shipped
  GLB with the existing `parseGlb` and uploads `Float32List` positions/colours;
  Kotlin has no glTF loader of its own. One model pipeline, one set of unit tests.
- **Station-local frame is left-handed on purpose** (`+X` right, `+Y` up, `+Z`
  forward). `(right, up, forward)` cannot be a rotation, so `StationFrame` carries
  a mirror in exactly two functions, `localToWorld` / `worldToLocal`. This makes
  "yaw +90° is to your right" literally true, which the spec requires.
- `AlignmentCalculator` reuses `Quat.toCameraFrame`, which already returns
  `(right, up, forward)` — so `atan2(x, z)` really is the right-turn correction.
- `StabilityMonitor` pruning bug found and fixed: a plain
  `removeWhere(at.isBefore(cutoff))` deletes the sample that proves the window
  elapsed, so `heldFor` can never reach the window and the shutter never fires.
  Fixed by keeping the newest sample at or before the cutoff.
- `analysis_options.yaml` excludes `tool/**`: those standalone verification
  harnesses import a `test/*_checks.dart` family that is not in this workspace,
  producing 39 permanent false errors.

- `com.google.ar:core` was pinned at `1.48.2`, which was **never published** to
  Google Maven (the 1.48 line only shipped `1.48.0`), so `assembleDebug` could not
  resolve it. Now `1.57.0`.
- `android.opengl.Matrix.multiplyMM` must not alias result with input —
  `buildModelMatrix` did.

### Verification

- `flutter analyze` — no issues.
- `flutter test` — 58 tests pass (26-target sphere, alignment incl. the required
  +20° validation case, angle wrapping, station frames, stability, and the
  controller's tracking/anchor/save gates).
- `flutter build apk --debug` — **built**:
  `build/app/outputs/flutter-apk/app-debug.apk`. This is what verifies the Kotlin.

Full report: `docs/SECTION1_CAPTURE_IMPLEMENTATION.md` (includes a device test

## Section 1 — device failure fix (black preview, GL exception)

Reported on a physical device: black AR view, `Tracking paused`, `0 planes`,
disabled Capture, and `java.lang.IllegalArgumentException: Must use a native ord…`.

**Root cause (one):** `ArGlRenderer.kt` built the camera quad and UV buffers with
`FloatBuffer.allocate(8)` — **heap** buffers — and passed them to
`GLES20.glVertexAttribPointer`, whose JNI rejects non-direct buffers with exactly
`Must use a native order direct buffer`. `drawCamera()` runs first in the render
loop, so the throw happened every frame and `renderFrame`'s catch swallowed it
*before* `eglSwapBuffers` → the Flutter texture never got a buffer → black. It also
skipped the raycast/still handling that sits after `draw()`, which is why the target
could never anchor and the Capture button never enabled.

Fix: one `directFloatBuffer()` helper (`ByteBuffer.allocateDirect().order(nativeOrder())`)
used by the quad, the UVs and the mesh upload. Not a Dart problem — no Dart workaround.

Also fixed in the same pass:
- shaders are `val … .trimIndent()` so `#extension` is the first token;
- `Matrix.multiplyMM` aliasing in `buildModelMatrix`;
- render failures now report `Class: message` + first stack frame + `fatal`, once
  per distinct signature, and the screen shows them in a red banner with **Retry**;
- `measureImageAxis`/`emitPose` wrapped in `runCatching` (they can throw before
  display geometry settles, and a throw there also skips the swap);
- `rescan` channel method: re-arms plane finding, drops anchors, re-sends display
  geometry — *without* restarting the session, so the station pose survives;
- `readyToCapture` is now `captureBlockReason == null` and **requires the stability
  window** (it previously enabled on alignment alone); the reason is printed in the
  UI;
- secondary button is always defined (Scan again / Retake) instead of vanishing;
- banner + mini-map moved below the status bar (`MediaQuery.paddingOf`).

Assets: `pubspec.yaml` now names both GLB paths explicitly. Verified present in the
APK at `assets/flutter_assets/assets/models/*.glb`, 12608 / 10088 bytes. No second
copy under `android/app/src/main/assets/` — Kotlin has no glTF loader; it receives
triangles over the channel.

Verified: analyze clean, **63 tests pass**, APK builds. Still device-only: that the
preview is visible, that ARCore reaches TRACKING, that both models render, that the
button gates correctly, that a saved photo is upright and overlay-free.

Report: `docs/SECTION1_DEVICE_FIX_REPORT.md`.

## Section 1 — ARCore / GLB verification pass

Confirmed native ARCore is the integration (gradle `com.google.ar:core:1.57.0`,
manifest meta-data, no Flutter AR package, session created in
`ArCoreSessionController.start()`). Reported the exact session-creation and
per-frame render code before changing anything.

**Zero-plane cause, two parts:**
1. *Certain defect:* `emitPose` read `camera.imageIntrinsics` **before** `emit()`.
   If that threw, no pose event was ever sent → `planesTracked` stuck at 0, tracking
   never advanced, nothing could anchor. The old `runCatching` hid it. Now the pose
   and plane counts are built first and always emitted; intrinsics are best-effort;
   failures are reported.
2. *Environmental:* an empty unit with white walls / glossy floor genuinely yields
   0 planes. Now diagnosable: counts broken down as walls/floors/ceilings.
Plus: `rayDistanceM` 4 m → **8 m** (a 6 m unit gave "no surface" on a mapped room),
and raycast misses now carry a reason (`no_candidates` vs `no_plane_within_range`)
instead of a bare null.

**GLB facts, read from the glTF JSON chunks (not assumed):**
- Both files: POSITION only, indexed, mode 4. **No** textures, images, UVs,
  normals, COLOR_0, node transforms, or KHR extensions. Materials are
  baseColorFactor + doubleSided only.
- target: 4 meshes = 256 + 256 + 12 + 12 tris (536); plate 0.54×0.54×0.006 m;
  meshes 2/3 are the two 8-vert/12-tri check-mark cuboids.
- bezel: 256 verts → 512 tris, 0.70 m, baseColor 0.95 grey.
- ⇒ the position+flat-colour pipeline is *complete* for these assets, not an
  approximation. Verified by `test/glb_pipeline_test.dart` (11 tests) which loads
  the real files through `GlbMeshSource.load(loader:)` and asserts counts, the
  index expansion (256 tris ⇒ 768 verts), colours, and 0.54 m proportions.

**Bezel setback correction:** first set 2 mm — wrong, the bezel is 12 mm deep and
the plate 6 mm, so anything under ~6 mm puts the bezel in front of the plate and
covers the green centre. Now **14 mm** (clears the plate by 8 mm, no coplanar
contact). Also `getProjectionMatrix` near 0.02→0.05, far 100→50 for 16-bit depth
precision at 2 m.

`skipCheckMarks` now goes through `GlbTargetTopology.isCheckMarkPart()` instead of
`meshIndex >= 2`, so a changed asset drops nothing rather than the wrong thing.

Verified: analyze clean, **74 tests pass**, APK builds. Still device-only: whether
ARCore finds planes, whether the anchor is created, whether the marker appears.
Report: `docs/SECTION1_ARCORE_GLB_VERIFICATION.md`.

## Section 1 — lifecycle bug found from a device screenshot

Screenshot showed `Tracking tracking · 0 planes` with a calibrated Target 1 and a
disabled shutter reading **"AR is still starting."** — a contradiction, because a
target only exists after calibration (which sets phase to `capturing`).

Cause: `didChangeAppLifecycleState` treated `inactive` as a resume.
`inactive` fires for the notification shade / app-switcher preview / camera
permission dialog — none of which stop the session — and each one re-ran `boot()`,
resetting the phase to `scanning` while `station` and `targets` survived. So the
gate returned "AR is still starting." for the rest of the session.

Fixes:
- screen: only `resumed` resumes; `inactive` is a no-op.
- `boot()` cancels any existing pose/diagnostic subscriptions first (a second boot
  was leaving two listeners, which could advance the stability clock twice and fire
  the shutter twice).
- `onAppResumed()` now restores the phase: if the host **reused** the session
  (`ArCoreSession.reused`, same world origin) the station is reattached and the
  active target re-anchored; if the session was **restarted**, the station is
  discarded with an explicit message, because a new ARCore world origin would aim
  all 26 targets at the wrong place.
- `CaptureState.copyWith` gained `clearStation` — `station: null` silently kept the
  old value, so both discard paths (`retrySession`, restart-on-resume) were no-ops.
- boot banner "Move the phone slowly…" is cleared once tracking is live, and
  `_trackingAdvice` now has a truthful TRACKING branch (it previously fell through
  to "tracking stopped").
- detail line reads `AR tracking OK` instead of `Tracking tracking`.

Verified: analyze clean, **77 tests pass** (+3 lifecycle), APK builds.

## Section 1 — target composite: measured setback (0.020 → 0.006)

Measured both GLBs from their JSON chunks + expanded index buffers:
- plate  : disc  r 0 → 0.270, z 0 → 0.006, centre (0,0)
- green  : disc  r 0 → 0.100, z 0 → 0.012
- checks : 2 cuboids, z 0.012 → 0.018 (offset ticks)
- bezel  : torus r 0.270 → 0.350, z 0 → 0.012, centre (0,0)

⇒ centres coincide (no compensation needed); bezel inner radius == plate outer
radius, so the ring *surrounds* and *abuts*, never overlapping in x/y.

**The old 20 mm was justified by a false claim** ("120 bezel triangles inside the
plate footprint" — those are the inner wall, centroid r 0.2697 vs 0.270, a
rounding artifact). Recessing the ring makes it project *smaller*, so the nearer
plate overlaps the ring's inner edge — the error is overlap, not a gap, and it
crosses zero at exactly one value:

```
0.020 → +3.8 mm overlap   0.014 → +2.2 mm   0.006 → 0.00 (exact)
0.002 → −1.1 mm daylight  0.000 → −1.7 mm
```

0.006 is that crossover and equals `0.012 − 0.006` (the two front faces become
coplanar). Applied to BOTH renderers: `arBezelSetbackM` (legacy 2D) and
`CaptureGeometryConfig.bezelSetbackM` (AR/native). Corrected the false claim in
`glb_target_overlay.dart`'s limitation note too.

Added `tool/render_target_preview.py` — a dependency-free software rasteriser that
parses the real GLBs, applies the same billboard + pinhole + `shadeFloor 0.55`
flat shading as `glb_renderer.dart`, z-buffers and downsamples 2× — plus
`tool/render_target_compare.py` for the 3-panel sheet. Outputs in `docs/previews/`.

**Honest finding:** both ring and plate are baseColor 0.95 white and now flush, so
head-on they render as ONE white disc with a green centre — the ring has no
visible boundary because the assets contain none. Did not fake a seam. If the
reference shows a distinct ring it needs a gap (<0.006), a colour difference
(asset change, needs approval) or a UI stroke. Reference image was never attached.

Tests: 86 pass (+9 geometry: concentricity, abutment, hollowness, green centre,
check-mark height, flushness, crossover, both-renderers-agree). Analyze clean,
APK builds. Report: `docs/SECTION1_TARGET_COMPOSITE_FIX.md`.
