## Device screenshots: capture blocked by drift — and the app caused the drift

Screenshots showed: "AR tracking OK · no planes yet", 26 markers scattered at
wildly different sizes, drift 2.19 m / 2.03 m, error 38.8° / 46.1°, "Walk back

`Move to target` and the instruction said "Move to the front target. Turn

around the station they have left. Added `recalibrateHere()`: releases the old

## Video: "Saving…" hang at 0/26, oversized disk, contradictory status

**1. The hang — a native still request nobody consumed.**
`takeStill` sets `pendingStill` and the render loop consumed it *after*
`transformCoordinates2d` / `renderer.draw`; any persistent failure in those left
`pendingStill` set forever and the Dart future with no deadline. Fixes, all
three layers:
* Kotlin: consume the still **immediately after the frame exists**, before any
  call that can throw, in its own try/catch.
* Kotlin: `answerPendingStills()` drains queued callbacks in `stop()` and
  `dispose()` — a request abandoned by a stopping session is answered with
  `no_session` instead of hanging.
* Dart: `PhotoCaptureService` now has `stillTimeout` (6 s) and `saveTimeout`
  (10 s) around takeStill / write / read-back / saveRecord, each turning a hang
  into a `StorageFailure` with a stated stage, plus one `[capture] +Nms
  stage=…` log line per stage (unconditional; 26 lines per station).

**2. Contradictory status.** `instruction` never checked `capturing`, so the
big line read "Ready to capture. Hold still." while the chip read "Validating
image" — exactly the video. `capturing` now returns "Saving the photograph…"
first.

**3. Oversized disk — the scale was not actually applied.** The normalisation
lived only inside `_loadMeshes()`, which early-returns when the controller is
constructed with preloaded meshes → the scene drew at the authored 1.0 (the
0.54 m plate). Extracted `_applyMarkerScale()` and call it on every `boot()`.
The new scene-level test (all 52 draws at `markerScaleFor(0.54)`, plate =
0.22 m) is what caught it.

Tests: new `test/photo_capture_service_test.dart` (6 — real file written and
verified, validation floor, record-write failure retryable, **camera that never
answers fails at the deadline**, duplicate shutter refused with one request,
stage timings logged), +1 scene-scale test in capture_progress_test.
295 tests pass, analyze clean, APK built (Kotlin compiled).

## Pipeline audit (sphere → StationFrame → resolveTarget → projection → GLB)

Audited all seven files. **No transform defect found; the missing piece was
projection tests, now added.** Findings worth keeping:

* `directionFromYawPitch` (there is no `sphericalToVector`; this is it) —
  `(cos p·sin y, sin p, cos p·cos y)`, navigation yaw (0 → +Z, +90 → +X, +Y up,
  ±90 poles exact, yaw term vanishes). Five call sites.
* `StationFrame` — gravity-aligned reference; `localToWorld` mirrors x
  (`rotate(-x, y, z)`) so station-local +X (right) survives the camera
  handedness. **The mirror is what makes a yaw +90 target land on screen-right.**
* `resolveTarget` — single authority: `P0 + r·d̂`, facing `−d̂`,
  `facingRotation`; `placeAll` calls it, the sphere map projects the same
  `spec.direction`.
* `project()` — pinhole, `u = W/2 + fx·x/z`, `v = H/2 − fy·y/z`; behind the
  camera and the poles have no projection (edge-pinned with a direction).
* **`GlbTargetScene` is intentionally a screen-space overlay** for the *tour*
  flow (`glb_target_overlay.dart`), not the 26-target capture path. Its screen
  coordinates come from `project()` of the real world point
  (`renderer.setPlacement(screenX: p.u, screenY: p.v)`); the 1 m depth only
  sizes the billboard (`arTargetDistanceM`). The capture screen draws natively
  from world anchors (`buildDraws` reads `anchor.pose` every frame), so it never
  uses a screen ray.
* `glb_renderer.dart` uses the same pose convention (`pose.rotate(unitZ)` =
  optical axis) and derives `fx/fy` exactly as `project()`.
* **Convention to remember**: for an identity pose (facing +Z), world **−X** is
  screen-right, because `toCameraFrame` negates x.

Tests: new `test/projection_test.dart` (10 — hand-computed pixels for
front/back/left/right/up/down, the 45° edge, behind-camera, poles, all 26
targets centred + zero alignment error when aimed, yaw ±45 halves, upper/lower
halves, 10° turn = fx·tan(10°) px, and the sign invariant "turn right == right
of centre"). 305 tests pass, analyze clean, APK built.

## FIX: the alignment arrow did not point at the GLB target

**Root cause (confirmed by source, not assumed).** `_ArrowPainter` drew along
`atan2(−pitchCorrectionDeg, yawCorrectionDeg)` — an *angle*. The pixel offset a
direction actually produces is `fx·tan(yaw)` by `fy·tan(pitch)`, and on a
portrait display `fy ≈ 1.6·fx` (1080×2400 screen, display FOV ≈ 53.7°×68° →
fx≈1069, fy≈1779). So the arrow was correct in every quadrant and up to ~15°
wrong in every diagonal — right at small errors, visibly off at large ones. It
also never called `project()`, so it could not tell "in view" from "off screen /
behind the camera". The capture feature was the only part of the app that did
not use the projection contract.

**Not defects (checked and cleared):** `directionFromYawPitch`, `StationFrame`
mirror, `resolveTarget`, `facingRotation`, `AlignmentCalculator` (yaw/pitch/3-D
signs all correct), native `buildDraws` (draws at `anchor.pose`, model matrix =
`anchorMatrix · R(localRotation)` then offset then scale → plate centre =
`placement.worldPosition`), `_placement` IS updated from `refresh()` every
500 ms.

**Changes** (no new architecture, no new projection formula):
* `target_alignment_overlay.dart` — `_ArrowPainter` now calls
  `project(alignment.directionInCamera, size.w, size.h, hfov, vfov)` and draws
  from the screen centre towards that pixel; shaft length still grows with the
  3-D error but stops at the marker (`min(wanted, targetDistance − wing)`) and
  is clipped at the viewport edge (`_distanceToEdge`, 12 px inset like
  `project`'s pin) so off-screen/behind targets leave a chevron on the correct
  side. Poles go through the same call — no yaw involved. Hidden inside
  tolerance (display only; shutter still reads `captureBlockReason`).
* New required `displayFov` param; `CaptureState.displayFov` =
  `intrinsics?.portraitDisplayFov() ?? ArCameraIntrinsics.fallbackDisplayFov`.
* `ar_types.dart` — added `fallbackDisplayFov` static getter so the provisional
  68° lives in one place.
* `ar_capture_screen.dart` — passes `displayFov`, and
  `anchored: activeAnchored && activeAnchorTracking` (a paused anchor is not
  drawn, so the arrow must not point at an invisible marker).

`glb_target_scene.dart` / `glb_renderer.dart` untouched — they are the tour-flow
software overlay, not the native 26-target path. No tests/analyze/build run
(per the brief).

**Limitation:** the GLB is drawn at the anchor's live pose while Dart aims at
`placement.worldPosition`, refreshed from the host every 500 ms — a bounded
lag while ARCore refines a new anchor. Removing it would need a per-frame
anchor pose in the pose event (a Kotlin + Dart channel change) or 30 channel
calls/s; not done. Also unverified on a device: the preview's effective FOV
(centre-crop vs. fill) — no hardware attached.

## FIX: targets vanishing on rotation, and hiding the target on a full ring

**Bug 1 root cause (two parts, both policy not maths — placement was correct):**
* `ArSceneDraw.requireTracking` defaults to `true`, so `ArCoreSessionController.
  buildDraws()` (line 648) dropped every draw whose anchor was not `TRACKING`.
  ARCore *pauses* a world anchor whenever its own tracking degrades (fast turn,
  featureless wall) and resumes it by itself → the marker vanished on every
  rotation even though its pose never stopped being the position we placed.
* Worse: `_refreshAnchorIfDue` counted the pause (6 refreshes ≈ 3 s) and then
  **re-placed** the target — release + create. The replacement starts paused
  too, 2 rounds hit `kAnchorReplacementsMax`, `_anchorGiveUp` latched, and the
  marker never came back. That is the "disappears permanently" report.
  Fixes: `pushScene` now passes `requireTracking: false` for capture targets
  (world anchors = our own position; the plane-attached flow keeps the strict
  default), and the pause branch only *waits* — re-placement is now reserved
  for `gone` (host no longer has the anchor), still bounded.
  Confirmed correct and untouched: `buildDraws` reads `anchor.pose` per frame,
  model = `anchorMatrix · R(localRotation)` → translate(offset) → scale,
  `viewProjection = P·V`, `mvp = viewProjection · model`.

**Bug 2 root cause:** nothing hid anything. `pushScene` drew every placed
target, done ones at FULL opacity. Fix: `pushScene` takes `hiddenTargets` and
**omits** those ids (anchor + placement + record untouched). The controller's
new `_pushScene(s, {targets})` is the single push path (tint/done/hidden can no
longer disagree) and `_hiddenTargetsIn()` hides every `isDone` target plus the
active one while `shotPhase` is `capture`/`validate`/`accept`. Reusing the
derived phase is the point: `ShotPhase.capture` == "tracking, aimed, steady,
in tolerance, at the station, not saving", i.e. exactly the ring-full state;
`retry` (failed) and `align`/`settle` (hold lost) restore it. One push per
transition (`_sameHidden` guard) so a 60 Hz pose stream costs nothing.
`kAnchorRetrackRefreshLimit` deleted; `selectTarget` now pushes *after* its
emit so a pose-driven push cannot re-highlight the previous selection.

## Round 3 (screenshot: "AR tracking paused · no planes · Initialising · drift 0.93 m")

Traced all four reported problems. **Two were already fixed in round 2 (the
user is almost certainly running an older APK); two were real and are fixed now.**

* **Spherical arrangement — no defect found.** `resolveTarget` = `P0 + 1.5·d̂`
  through `StationFrame.localToWorld` (the x-mirror is what puts a yaw+90 target
  on screen-right); `_onPose` never recomputes a placement; anchors are created
  once at calibration; `selectTarget`/`_demoteActive` only move status. Native
  `buildDraws` reads `anchor.pose` per frame, model = `A·R·T(offset)·S`,
  `viewProjection = P·V`. The disappearance was the round-2 defects.
* **Shrinking — no scaling defect.** `markerScale` is set once at boot
  (`_applyMarkerScale` → `markerScaleFor(0.54) ≈ 0.407`) for plate *and* bezel,
  and `ArSceneDraw.scale` is never re-derived. Apparent shrink = perspective.
  Added a detail line "Plate 0.22 m across · N.NN m away" so the two are
  distinguishable on screen.
* **`AR tracking paused` — real defect: the instruction line.** `starting`/
  `scanning` are decided by the *last pose*, so while ARCore is paused the
  phase never leaves `starting` and the main line said "Starting the AR
  session…" forever; the actionable advice existed only in the *expanded*
  detail. Fixed: `CaptureState.trackingGuidance` (new, reason-aware — carries
  ARCore's INSUFFICIENT_LIGHT / EXCESSIVE_MOTION / INSUFFICIENT_FEATURES /
  BAD_STATE / CAMERA_UNAVAILABLE) now feeds `instruction` for the pre-capture
  phases, and the screen's `_trackingAdvice` delegates to it (single source;
  `_failureReasonAdvice` deleted). Also: detail says "Planes are not needed —
  targets are placed from the station" when tracking is live with 0 planes,
  and the paused-anchor copy no longer claims the marker is invisible.
* **Hide on green ring — implemented in round 2, re-verified.** `shotPhase ==
  capture` is exactly `withinTolerance && stable && tracking && fresh &&
  anchored && !drifted && !saving` — i.e. the ring-full state *and* the ready
  state, which is what the brief asked for. The only divergence is drift
  (0.93 m in the screenshot): ring full, phase `align`, target stays visible,
  capture blocked with "walk back / Recalibrate here". Deliberate — the drift
  check must stay.
* **`requireTracking: false` is honoured natively**: plugin parses
  `item["requireTracking"] as? Boolean ?: true` and `ArSceneDraw.toMap` sends it.
