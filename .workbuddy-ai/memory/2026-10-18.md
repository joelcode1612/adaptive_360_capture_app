## Research — webcammictest.com/sensors methodology (no code changed)

User observed that page's sensors feel accurate and asked how it works. Scope A+B
(claims + source). No `lib/`, `test/`, `tool/` or `android/` file touched — verified
with `find -newermt`; only `docs/RESEARCH_SENSOR_METHODOLOGY_webcammictest.md` added.

Method: the page is Next.js/Turbopack, so WebFetch only returned rendered text.
Downloaded the HTML plus 12 chunks; all sensor logic is in
`/_next/static/chunks/ff2cad39b406c13f.js` (47,634 B). Read the minified source
directly.

### Findings worth keeping

- **Stack:** Generic Sensor API first (`Accelerometer`, `Gyroscope`,
  `Magnetometer`, `AbsoluteOrientationSensor`, …) constructed at
  `frequency: 60`; falls back to `devicemotion`/`deviceorientation`. Reports which
  path it used and the **measured** rate (1 s windows).
- **Permission:** no prompt unless `DeviceMotionEvent.requestPermission` exists
  (iOS). Instead it listens for **700 ms**; an event arriving unaided ⇒ already
  granted, else show the tap button. Support is asserted only on non-null values.
- **Attitude = gravity only, zero filtering, zero gyro fusion:**
  `up = ±a/|a|`, `pitch=asin(up.y)`, `roll=asin(up.x)`, `tilt=acos(up.z)`,
  reject `|a| < 0.5`. This is why it *feels* accurate: pitch/roll are absolute and
  cannot drift.
- **Sign auto-calibration:** compares `sign(up.y)` with `sin(beta)`, latching ±1.
  Cheap fix for the "bubble moves the wrong way" class of bug.
- **Heading:** `webkitCompassHeading` (iOS) else `360 − alpha` when absolute;
  absolute/relative merge keeps the old alpha so the compass can't flap.
- **Compass sweep:** 16 sectors × 22.5°, `round(heading/22.5) % 16`; complete at 16.
  `webkitCompassAccuracy < 0` ⇒ "uncalibrated" (hard fail).
- **Two-position level calibration:** hold, turn ≥160°, hold. Closed-form 2×2
  solve separating surface tilt from device offset. Verdict on `offset`:
  ≤0.3° accurate, ≤1° slight, ≤2.5° off, else bad. Flat = `tilt ≤ 0.5`.
- **Drift at rest:** 20 s, disturbed if `|ω| > 4 °/s` or `||a|−g| > 0.6`. Reports
  per-axis σ, gravity bias, `tiltWander`. Acceptance table:
  gyro bias ≤0.1 °/s steady / ≤0.5 slight / ≤2 noticeable;
  accel |Δg| ≤0.06 & σ ≤0.05 steady, etc.
- **Shake:** `>14 m/s²` above gravity, debounced 400 ms; `peakG = peak/g`.

### Contrast with this app

App: `sensors_plus ^7.1.1` → `SensorPoseSource` + `AttitudeFusion` (complementary,
β=0.05, gyro integration). Page has **no yaw from motion at all** — yaw is the
platform compass. So the app's yaw is smooth but drifts; the page's cannot drift
but cannot give continuous rotation. For this app that trade is correct, because
target directions are relative to the heading locked at station calibration.

Three portable ideas, not yet implemented: (1) gravity-sign auto-calibration,
(2) two-position offset solve, (3) disturbance gating (`|ω|>4 °/s`,
`||a|−g|>0.6`) in `StabilityMonitor` — cheaper than a pose delta for detecting
"the phone is being carried".

Page is a diagnostic, not a library: minified hashed chunk, no API, no source-map
guarantee. Cannot be imported or embedded.

Report: `docs/RESEARCH_SENSOR_METHODOLOGY_webcammictest.md` (434 lines).

## Motion stability implementation (Phase A–L)

Baseline recorded in `docs/BASELINE_motion_stability.md`: Flutter 3.44.6 / Dart
3.12.2; deps camera/sensors_plus/wakelock_plus/permission_handler/path_provider/
path/panorama_viewer — **no `ar_flutter_plugin`, no `vector_math`, no
`camerawesome`**; 86 tests, analyze clean.

**The brief's 360° yaw-tolerance risk does not exist here.** Both paths gate on a
geodesic angle (`AlignmentCalculator` 3°; legacy `aim().angleDeg < 2.5`). No
per-axis yaw comparison anywhere. Pinned by a new test.

**Strategy chosen: A.** The AR path's source is ARCore's already-fused pose, so no
second complementary/Kalman filter on it. Added a **display-only**
`AdaptiveQuaternionSmoother` (`alpha = 1-exp(-dt/tau)`, `Quat.slerp`, snaps on no
state / gap > 0.5 s / jump > 25°). The legacy sensor path keeps its existing
`AttitudeFusion` (β=0.05) — not duplicated. EKF rejected and documented: no ground
truth for covariances, no raw mag on the AR path.

New module `lib/features/capture/domain/motion/`: `motion_sample.dart`
(+`angleBetweenDeg`, `angularRateFromQuaternions`), `orientation_filter.dart`,
`adaptive_quaternion_smoother.dart`, `shot_phase.dart` (derived state machine, not
a second gate), `motion_diagnostics.dart` (bounded CSV/JSON, no personal data).

**Two defects found by tests, not inspection:**
1. Differencing *consecutive* poses turns ±0.35° jitter into **21 °/s** — the 5 °/s
   gate would refuse a still phone. Fixed with a **100 ms `rateBaseline`** (→0.33 °/s)
   plus a refusal-proof rate history.
2. `_smoother.reset()` on tracking loss was immediately undone because the *paused*
   sample re-seeded it. Fixed by bypassing the filter entirely while tracking is down.

`StabilityMonitor` extended (not duplicated): rate gate, measurement-age gate,
**quaternion** drift (catches roll; the forward-vector form cannot), `lastRejection`.
`stabilityWindow` 500→450 ms. Tolerance kept at **3°**, not the brief's 8° —
documented (8° of a 360° panorama is a visible seam; 8° is still available in config
for the sensor-only tier).

**Measured** (`tool/motion_comparison.dart` → `docs/measurements/`), synthetic
scripted truth at 30 Hz: jitter σ 0.002302→0.000802 (**−65%**), mean |error|
0.229°→0.081°, max 0.395°→0.249°, **settle +333 ms**. Gate on raw = 467 ms to
stable either way; gating on smoothed would be 933 ms — the measurement behind
keeping the gate on raw. Carried-while-aimed at 20 °/s: **2 false-readies baseline
vs 0 candidate** of 60.

Verification: pub get 0, format 0 (0 changed), analyze 0 (no issues), **145 tests
pass** (+59), `flutter build apk --debug` 0. **No device**: `adb devices` empty and
`flutter devices` blocked by the sandbox's `reg.exe` blacklist → device run not
performed. Decision: **Partially passed**.

Report: `docs/REPORT_motion_stability.md`.

## Capture quality fix (blurry saved photos)

User screenshot: capture screen, "the image very blur". Scope answer: blur is
in the **saved photographs**. Traced the whole pipeline and exonerated each
stage: `YuvJpegEncoder` (raw-plane rotation + one `compressToJpeg`, no
resampling), JPEG quality 95, EGL RGB888 at full physical pixels, `GL_LINEAR`
OES texture, passthrough camera quad, `FilterQuality` (preview-only), and
motion blur (stability gate settles the phone first).

Root cause: **`Config.focusMode` was never set** → ARCore default FIXED focus →
soft at the 30–70 cm capture distance, and it softens the saved stills too
because `acquireCameraImage()` uses the same lens. Second cause was
diagnosability: the session's camera config (CPU still size) was never
reported, so "soft lens" and "small stream" looked identical.

Fix: `config.focusMode = Config.FocusMode.AUTO` with a fallback path (device
refuses → default FIXED, session survives; readback reports the effective
mode). Added `readCameraConfig()` reporting `still/preview` sizes + fps +
focusMode on one pose event; `ArCameraQuality` (ar_types) +
`parseCameraQuality` (payload) + `ArPoseSample.cameraQuality` +
`CaptureState.cameraQuality` (clear on restart); status detail shows
`Photos {w}×{h} · autofocus on`.

User chose **keep ARCore's automatic camera choice** — if the readout shows a
low still resolution, the follow-up (explicit `session.cameraConfig` selection)
gets its own approval, not done preemptively.

Analyze clean, 182 tests (+11 `camera_quality_test.dart`), Kotlin compiles,
APK rebuilt. No device: focus behaviour and actual still resolution still
pending on the user's phone — device checklist is in
`docs/REPORT_capture_quality.md` §D.

## Invisible GLB target (arrow fine, marker not drawn) — root cause + fix

Symptom: AR tracking OK, guided arrow points correctly, but the 3D GLB target
never appears in the camera view.

**Root cause:** the native renderer correctly refuses to draw a mesh whose ARCore
anchor is not `TRACKING` (`ArCoreSessionController.buildDraws()` line 611;
ARCore docs: "This pose should only be used for rendering if getTrackingState()
returns TRACKING"). But Dart never read the tracking state it was already being
sent (`anchorMap` includes `"tracking"`, `ArCoreAnchor` parses it,
`AnchoredTarget.isTracking` exists). `selectTarget` emitted `activeAnchored:
true` unconditionally and `_refreshAnchorIfDue` ignored both a null refresh
(anchor dropped) and a paused one — so a placed-but-paused anchor was
indistinguishable from a drawn one. The arrow stayed correct because it aims at
`placement.worldPosition` (the pose the anchor was created with, always valid),
which is precisely why the two disagreed. World-space anchors (introduced when
placement stopped using raycast plane hits) are the likely trigger: they can
start paused where plane-attached anchors essentially never were.

**Fix:** new `CaptureState.activeAnchorTracking`; `selectTarget` reports
"Waiting for AR to stabilise the target…" when the anchor is paused;
`_refreshAnchorIfDue` recovers — dropped anchor → re-place; paused → wait
(kAnchorRetrackRefreshLimit = 6 refreshes ≈ 3 s) → re-place
(kAnchorReplacementsMax = 2) → latched named failure ("AR will not hold the
target…") so the terminal message can't be clobbered by the waiting line.
Replacement budget resets only on a genuine target switch or successful
tracking (NOT on the re-place path itself — that would unbounded it).
Debug marker (brief §4): `--dart-define=glb_debug_marker=true` draws the plate
3.5× magenta at the same anchor — separates placement errors from GLB
rendering errors.

Tests: `test/world_target_test.dart` now 9 (added 4 anchor-lifecycle: paused at
placement, tracking arriving, anchor dropped, persistent pause + latch). Fake
gateway: `anchorTracking` + `dropAnchor()` + refresh re-stamps tracking
(ARCore's is dynamic). **207 tests pass**, analyze clean, APK built. No device
(phone disconnected) — on-device check pending.

## Tracking-reliability audit fixes (new brief, two defects)

Audit of the brief's claims found two genuine defects (everything else verified
correct and already test-covered). Both fixed and gated:

1. **Drift never blocked the shutter.** `driftM` was measured and displayed
   ("drift 0.20 m") but nothing in `captureBlockReason` read it — a phone
   standing 5 m from the station, aimed and steady, saved a photograph
   composed from the wrong place. Fixed with one predicate
   `CaptureState.stationDrifted` (`driftM > geometry.stationDriftWarningM`,
   0.6 m, strict `>`), consumed by **three** surfaces so they cannot disagree:
   `captureBlockReason` ("You are 5.0 m from the station — walk back to it to
   capture."), `instruction`, and `deriveShotPhase` (drift outranks `stable`
   → `align`, so the chip can't show green "Ready" above a disabled button —
   the false positive the phase machine exists to prevent).
   **The auto-capture path bypassed `readyToCapture` entirely** (it read only
   `stable && withinTolerance`) — it now consults `next.readyToCapture`, the
   same single decision the button uses. The stability monitor catches the
   *walk* (position drift 0.03 m across its window); only this gate catches
   *standing still in the wrong place*.
2. **Non-finite payload components slipped through the parser.**
   `arcore_payload.dart`'s `_d` accepted any `num`, including NaN/Infinity —
   and **every comparison against NaN is false**, so a NaN drift passed
   `driftM > 0.6` silently (fail-open). Now a non-finite component makes the
   payload "incomplete" (`null` — the file's existing contract for a missing
   key, never an invented default). Same guard added to `arcore_ar.dart`'s
   plane-quaternion and image-axis reads via a shared `_finiteOr(v, fallback)`.

Placement of the drift branch inside `captureBlockReason`: after
target-identity, **before** placement/alignment — everything below is
measured from the station's frame.

Tests: new `test/arcore_payload_test.dart` (8: NaN/±Inf in position,
quaternion, derived fields → null; finite still parses; the
`NaN > limit == false` language semantics pinned; missing key and NaN give
the same null). `test/world_target_test.dart` +6 drift (blocked with distance
in the sentence, boundary 0.6 live / 0.7 blocked, phase not "Ready",
**auto shutter does not fire 5 m out**, button refuses, walking back
re-arms). `test/shot_phase_test.dart` +2 (drift outranks settle, saving
outranks drift). 207 → **223 tests pass**, analyze clean, APK built.

**Both regression tests were verified to fail without their fix** (reverted
each in turn): the parser tests reproduce the exact defect
(`ArPose(Vec3(NaN, …))` parsed as valid), and the auto-shutter test proves a
photograph was saved while the phone stood 5 m away.

Gotcha worth remembering: when the auto shutter fires mid-`emitStable`, the
target becomes captured and every later pose sets `stable: false` (the
`!isDone` branch) — so in a *broken* run that test fails on `stable`, not on
`capturedCount`. The assertions are ordered defect-first so a future
regression reads "a photograph was saved".
